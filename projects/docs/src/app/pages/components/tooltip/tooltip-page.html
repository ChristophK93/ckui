Tooltip

ckTooltip shows a short supplementary text for a control: after a short delay on mouse hover, at once on keyboard focus, and on a long-press on a touch screen. Import CK_TOOLTIP_IMPORTS from @ckui/core/tooltip; it holds CkTooltip. The text is plain text only and describes the control; it never names it. The bubble is a native popover in the top layer, so it also shows above a dialog, a drawer or a menu, and it needs no overlay code.

Examples

Icon-only buttons

The usual place: a row of icon buttons. A button with no text needs a name of its own, an aria-label; the tooltip adds what the name cannot say, and a screen reader reads it as the description. Hover the first button and wait, then move along the row: once one tooltip has shown, the next ones show at once, until the pointer has been away for 300 ms. A tooltip that only repeats the name is shown to sighted users but not wired to aria-describedby, so it is not read twice.

Positions

The bubble is above by default. Without room on the chosen side it flips to the opposite one, and along the other axis it shifts to stay inside the screen: the buttons at the edge of a phone still get a whole tooltip. start and end follow the text direction, so in an Arabic or Hebrew page start is the right. 

{{ samples.positions }}

In a dialog

A tooltip inside a dialog sits above the dialog and stays usable although the page behind it is inert. Escape hides the tooltip and nothing else; the next Escape closes the dialog. Open it, press Tab to the settings button and try it. 

{{ samples.dialog }}

Text, delay and control

The text, the delay and the disabled state can be bound. The open tooltip follows a text that changes, and ckTooltipDisabled hides it. #tip="ckTooltip" gives you show(), hide() and the isVisible signal. 

{{ samples.control }}

Disabled buttons

A disabled ckButton sets the native disabled attribute, so it cannot take focus and a tooltip on it is mouse-only: a keyboard or touch user never sees it. Never explain why something is disabled only in a tooltip. Put the reason where everyone reads it, next to the button.

On a touch screen

There is no hover on a phone, so the tooltip shows on a long-press: hold the button for half a second without moving. The press does not click the button, the native callout and text selection stay away, and the bubble hides 1.5 seconds after the finger lifts or on the next press anywhere. A tap is a tap and does nothing tooltip-related. Because a phone user may never find the long-press, the tooltip is never the only carrier of information.

Keyboard

The behaviour follows the tooltip pattern of the WAI-ARIA Authoring Practices: focus shows it, Escape hides it, and it is role="tooltip" pointed at by aria-describedby. There are no arrow keys, so right-to-left text changes nothing here except the side that start and end mean.

Accessibility

  • A description, never the name. While the tooltip is on, the id of the bubble is added to the host's aria-describedby (your own ids stay, and are given back exactly when the tooltip goes away). The host's name is never touched: an icon-only button needs its own aria-label, and development builds warn once when the host has no accessible name. When the tooltip text equals the name (case and spacing aside) it is not wired at all, so a screen reader does not read it twice.
  • The bubble is mounted, hidden, for as long as the tooltip is enabled, so the description is there for a screen reader that reaches the control without keyboard focus (virtual cursor, touch exploration). It is shown on keyboard focus too, which is when most screen readers read the description.
  • Hoverable and dismissable (WCAG 1.4.13). The pointer can move onto the bubble without it vanishing, Escape hides it without moving focus, and it stays until the pointer leaves, the focus moves on or it is dismissed.
  • Never the only carrier of information. Plain text only, no links or buttons in the bubble, and no way to reach it on a touch screen but a long-press. Anything a user needs to know belongs on the page. That includes why a button is disabled.
  • The text is white on dark in the light theme and dark on white in the dark theme, at least 4.5:1. In forced-colors mode the bubble is Canvas with CanvasText text and a CanvasText border. Under reduced motion it appears without a fade.
  • Browser support. The bubble is a native popover, so the tooltip needs the Popover API (Chrome and Edge 114, Safari 17, Firefox 125). Without it the tooltip is simply off: nothing is mounted, nothing is wired to aria-describedby, no key or pointer is handled. The host keeps working as if it had no tooltip, so never depend on it.
  • Nothing is shown for a host inside an inert page (behind a modal dialog). A tooltip that keyboard focus showed stays while the mouse crosses its host; hovering another host shows that one meanwhile and the focused one returns when the hover ends. On a text input only keyboard focus shows it, not a click or a tap.
  • The bubble sits on the page body in a layer marked data-ck-inert-exempt, so it keeps working above a modal dialog. It does not repeat the host's styles: a nested data-ck-theme or a class-scoped token on a wrapper does not reach it. Set the tokens on :root or on a theme selector.
  • Global element styles. The bubble is a plain <div> styled by a class in a layer. An unlayered reset such as * { padding: 0 } or div { background: none } beats it: the text loses its padding and its fill. Keep those rules off .ck-tooltip or put resets in a layer declared before ckui. The first rule below really breaks the tooltip; the rest scope it.
